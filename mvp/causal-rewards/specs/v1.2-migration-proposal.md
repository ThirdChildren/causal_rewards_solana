## Item B1 — pin the participant Merkle leaf form + sort key (§6.2)

**Currently:** `serialization.md` §6.2 stamps the participant leaf/sort as
`PROVISIONAL-UNPINNED-6.2` ("recommendation of record: participant id ascending"). The
`backend-data-engineer` bundle assembler already implements a concrete form; this item pins THAT form
as normative so the participant root is reproducible.

**Exact spec change (`serialization.md` §6.2, replacing the participant bullet):**

- **participant leaf preimage:** `canonical_leaf_bytes(p) = CJSON({"cohort_id": <string>,
  "participant_id": <string>})` — a §3 CJSON object (two ASCII keys; `cohort_id` sorts before
  `participant_id`). `leaf_hash(p) = SHA-256(0x00 || "CRP:participant:v1" || canonical_leaf_bytes(p))`
  (§6.1, `DOMAIN_TAG = CRP:participant:v1`, already in the domain-tag table).
- **sort key (total order):** `participant_id` ascending by **UTF-16 code-unit of the NFC-normalized
  id** (the same anti-insertion-order rule as assignment §6.2 / `cohort_id`). `participant_id` is a
  unique key within one experiment's participant set, so the order is total with no tie-break; a
  duplicate `participant_id` is a hard error. (If a future variant ever admits the same participant in
  two cohorts as two leaves, the sort key becomes `(participant_id, cohort_id)` — a versioned change,
  not this pin.)

**Why it moves a golden:** it pins the **participant root** and therefore the
`bundle_logical_hash` (`serialization.md` §8.1). It does **NOT** move the manifest golden
`74e0bb82…` or the evidence golden `901b08d5…` — the participant root is a bundle root, not a manifest
field. No participant golden is committed yet, so this is a first pin rather than a change to an
existing committed root; but any bundle that includes `participants.parquet` acquires a fixed
participant root on ratification, and that fixture must then be frozen.

**Computed cost (illustrative fixture, so the user sees concrete bytes):**
- one leaf: `CJSON({"cohort_id":"u4pruydqqvj","participant_id":"sensor-000007"})` →
  `leaf_hash = b559ceec313c46b03d1804e2a4d9f3a916a193dadf9a20fed805d9dec99b1be8`.
- two-leaf tree, participants `sensor-000007` and `sensor-000042` (same cohort), placed in the
  pinned `participant_id`-ascending order (`…007` before `…042`) →
  **participant root `f32410c11cec46460eae4c0a282dd0eecfeed1e81c0216584cec7bb1b844018b`**.
- manifest golden: **UNCHANGED** (`74e0bb82…`).

**Owner:** `verifier-reproducibility-engineer` (commits the first participant golden fixture under
`test-vectors/`), with `backend-data-engineer` confirming the assembler emits the identical leaf form.

**Acceptance check:** the verifier reproduces the participant root from `participants.parquet` alone;
a committed `test-vectors/participant/*` fixture pins it; `serialization.md` §6.2 loses the
`PROVISIONAL-UNPINNED-6.2` stamp.

## Item B2 — frozen-missingness design (folds spec-round items 3 + 6 into ONE decision)

**Currently:** the manifest has no evidence schedule and no missingness policy. The engine derives
the schedule from other frozen fields and **defaults** `missingness_policy` to the strictest option
`ineligible` (`causal-engine/docs/modeling-notes.md` §6.1). CLAUDE.md requires the missingness policy
to be **frozen before analysis** (Invariant 1); a defaulted, unfrozen policy is a latent
freeze-before-reveal gap.

**Exact schema change (`manifest.schema.json`):**

1. New **required** top-level object `evidence_schedule` (frozen pre-analysis; all values canonical
   integer strings, §2.1; all keys ASCII):

   ```jsonc
   "evidence_schedule": {
     "type": "object",
     "additionalProperties": false,
     "required": ["epoch_count", "epoch_seconds", "expected_cohort_coverage", "missingness_action"],
     "properties": {
       "epoch_count":              { "type": "string", "pattern": "^[1-9][0-9]*$" },   // count, scale 1
       "epoch_seconds":            { "type": "string", "pattern": "^[1-9][0-9]*$" },   // seconds, scale 1
       "expected_cohort_coverage": { "type": "string", "pattern": "^[1-9][0-9]*$" },   // micro fraction (1e6); see scale note
       "missingness_action":       { "enum": ["ineligible", "impute_cohort_mean"] }
     }
   }
   ```

   A frozen cross-field constraint binds `epoch_count · epoch_seconds` to the active window
   (`= active_end − active_start`), so the schedule is not a free third knob but a partition of the
   already-frozen window. A cohort-epoch counts as **present** iff its coverage ≥
   `expected_cohort_coverage`; otherwise it is **missing** and handled per `missingness_action`.

2. New **required** field `design.parameters.missingness_policy ∈ {ineligible, impute_cohort_mean}`
   (the value the engine consumes; default was `ineligible`).

3. **Single-source-of-truth reconciliation (the "one decision"):** a frozen equality constraint
   `evidence_schedule.missingness_action == design.parameters.missingness_policy`. The two fields are
   deliberately the SAME decision surfaced at two layers (schedule-detection vs valuation); the
   equality constraint prevents them diverging. `ineligible` = a cohort with any missing expected
   epoch is forced ineligible (Stage-1 minimum-sample path, `reward-policy.md` step 4). The engine
   defaults away — it reads the frozen value and MUST NOT substitute its own default.

   > **Architect note (recommend at ratification):** the cleanest end state collapses this to ONE
   > field. I recommend `design.parameters.missingness_policy` be the sole normative knob and
   > `evidence_schedule` carry only `{epoch_count, epoch_seconds, expected_cohort_coverage}` (drop
   > `missingness_action`), removing the equality constraint entirely. The union form (with
   > `missingness_action` + equality) is presented here because the spec round named both fields; the
   > collapsed form is strictly simpler and equally expressive. **The computed cost below is for the
   > union form as specified;** the collapsed form yields a different (also-computable) hash and I will
   > recompute it if the user prefers it.

**Scale note (must resolve at ratification):** `expected_cohort_coverage` is a fractional coverage
value but its name lacks the `_micro` suffix that §2.2 requires for the micro class. Resolve by either
(a) renaming to `expected_cohort_coverage_micro`, or (b) adding it to the §2.2 scale table as a named
micro exception. The computed cost below uses the literal name `expected_cohort_coverage` with a micro
value `"950000"` (0.95); option (a) would change the key bytes and therefore the hash.

**Why it moves the golden:** two new **required** manifest fields ⇒ the example manifest must carry
them ⇒ the manifest hash changes. `reward_curve_hash` is unaffected.

**Computed cost** (example manifest + `spec_version` `"1.2.0"` + `evidence_schedule`
`{epoch_count:"7", epoch_seconds:"86400", expected_cohort_coverage:"950000",
missingness_action:"ineligible"}` + `design.parameters.missingness_policy:"ineligible"`):

> **manifest golden `74e0bb82…` → `ac2b4bdc77a1eda506c2412a6139fbfa7676547d6759d08d286af91f06f249a3`**
> (`reward_curve_hash` unchanged `sha256:14b0ec34…`)

**Owner:** `protocol-architect` (schema + `serialization.md` §2.2 scale entry + example re-freeze),
then `backend-data-engineer` (schedule derivation reads the frozen field) and
`causal-inference-engineer` (engine reads `missingness_policy` instead of defaulting).

**Acceptance check:** schema validates the amended example; the new manifest golden is recorded in
`manifest.golden.md` and `golden-hashes` memory; the engine reads the frozen policy (no code default
path taken); `serialization.md` §2.2 lists the coverage field's scale.

## Item B3 — multiplicity + concentration control (Part C outcome, IF adopted)

This item exists only if the Part C recommendation (`specs/multiplicity-recommendation.md`) is
adopted as the **default** policy. It has two frozen-field effects; both are hash-moving. **The frozen
default stays `none` until the user signs off** — this is the migration that would change it.

**Exact schema change (`manifest.schema.json` `reward_policy`):**

1. New optional-then-required object `multiplicity_control`:

   ```jsonc
   "multiplicity_control": {
     "type": "object",
     "additionalProperties": false,
     "required": ["method"],
     "properties": {
       "method":         { "enum": ["none", "benjamini_hochberg", "bonferroni", "sidak"] },
       "fdr_level_micro": { "type": "string", "pattern": "^[1-9][0-9]*$" }   // required iff method=benjamini_hochberg
     }
   }
   ```

   The BH selection is deterministic given the frozen p-values (`multiplicity-study.md`), so it is
   frozen-manifest compatible. The candidate family `m` is the eligible + identified + causal-design
   cohort set (fixed by the frozen plan), so `m` is knowable at analysis time from frozen inputs only.

2. **Conservative-effect floor (concentration lever) — NO new field.** The floor is expressed by
   adding a breakpoint `["<floor_s>", "0"]` to the EXISTING `reward_curve.breakpoints` (below the
   floor, `alloc_c = 0`). This needs no schema change — it is a reparameterization of the already-frozen
   curve — but it **changes `reward_curve_hash` and therefore the manifest hash.**

**Why it moves the golden:** `multiplicity_control` is a new manifest field, and the floor breakpoint
changes `reward_curve` bytes ⇒ both `reward_curve_hash` and the manifest hash change.

**Computed cost** (floor breakpoint `["50000","0"]` inserted; `multiplicity_control =
{method:"benjamini_hochberg", fdr_level_micro:"50000"}`; layered on the Item-B2 baseline +
`spec_version "1.2.0"`):

> floored **`reward_curve_hash` `sha256:14b0ec34…` →
> `sha256:0123783ea8be8a6af3a2104df29a840a681e025d48fafad6a05c1946e8a1e7d3`**
> full v1.2 manifest (B2 missingness + B3 BH + B3 floor + `spec_version 1.2.0`):
> **manifest golden `74e0bb82…` → `98490aa37dd8c61f2b8d1c131e96ed8e46eb8f68306033ee31cafa99e23bb483`**

**Owner:** `protocol-architect` (policy + schema + curve), `causal-inference-engineer` (BH selection
layer + floor in the compiler; the study harness already implements BH).

**Acceptance check:** the multiplicity study's `benjamini_hochberg` column is reproduced by the engine
