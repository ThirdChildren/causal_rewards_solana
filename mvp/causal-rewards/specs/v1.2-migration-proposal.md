## Slot S2 — RETIRED (measured 2026-07-29; costs retained for the record)

**Ruling.** S2 is retired as a hash-moving multiplicity field. The study
(`docs/multiplicity-study.md`, pinned in `causal-engine/tests/test_levers.py`) settled every open
question; `specs/multiplicity-recommendation.md` §4 carries the full rationale. Summary:

- **Floor (C-2/C-3): struck.** Any floor that removes a null winner removes *only* the small one
  (`cell0048`, `conservative_s = 0.018384`) — the exact cohort BH already removes. The large null
  winner (`cell0007`, 0.139576) exceeds every true positive in the benchmark, so no floor separates
  signal from noise. Floor is dominated and redundant at every tested parameter; it pays a
  `reward_curve_hash` move for zero marginal effect.
- **Cap (C-4/C-5): needs NO new field.** A per-cohort cap is reproduced to the ppm by a *saturating*
  `reward_curve` (study arm 6b == arm 5). `reward_curve`/`reward_curve_hash` are already in
  `reward_policy.required`. It is the only lever that improves targeting (waste-to-legit
  0.402→0.245) and drops no true positive — but it lives in the existing frozen curve, so it is a
  **curve-shape / fixture** choice, not a new manifest field. `max_cohort_share_micro` is therefore
  **not proposed**.
- **BH (C-1): not worth a new frozen field on this evidence.** It is the only candidate needing a new
  frozen field, its concentration benefit is nil (25.94%→25.94%), its waste benefit is thin
  (29.6%→25.9%), and it costs true-positive power (`s5` 62.5%→37.5%). Keep it available as a
  documentable `multiplicity_control` value an experiment MAY freeze; do not add it to v1.2.
- **C-R (curve recalibration): free, adopt as guidance.** Cuts exposure hard (waste 29.6%→2.5%, max
  share 25.94%→2.16%) at zero power and **zero spec-hash cost**, but its waste-to-legit ratio never
  moves — it is an *exposure* fix, not a *targeting* fix, and must not be sold as a false-positive
  remedy. Adopt under "Reading B" (fixture + published guidance) in
  `specs/multiplicity-recommendation.md` §4a: it moves **no spec golden**.

## Slot S1 — Item B2: frozen-missingness design (APPROVED v1.2 scope: missingness ONLY)

**Currently:** the manifest has no frozen missingness policy. The engine reads
`design.parameters.missingness_policy ∈ {ineligible, impute_cohort_mean}` and **defaults** to the
strictest option `ineligible` when the field is absent
(`causal-engine/src/crp_engine/manifest.py:236` `params.get("missingness_policy", "ineligible")`;
`causal-engine/docs/modeling-notes.md` §6.1). CLAUDE.md requires the missingness policy to be **frozen
before analysis** (Invariant 1); a defaulted, unfrozen policy is a live freeze-before-reveal gap — an
analyst can change how missing cohort-epochs are handled *after* seeing data by changing code, and no
frozen field contradicts them.

**APPROVED FORM (owner, 2026-07-30): the COLLAPSED single-field form — "frozen missingness ONLY".**
The prior draft of this slot proposed a *union* form (a whole `evidence_schedule` object +
`missingness_action` + an equality constraint, golden `ac2b4bdc…`). That is **superseded.** The
engine consumes exactly one knob — `design.parameters.missingness_policy` (verified: `panel.py:200–218`
branches on this field alone; there is no coverage-threshold presence-detection path in the engine
today). Freezing that one field closes the exact Invariant-1 hole the engine has. The
`evidence_schedule` object and the `expected_cohort_coverage` scale-table question are NOT part of
this landing (they address a *separate*, not-yet-live concern — what counts as a *present*
cohort-epoch — which the engine does not currently gate on a frozen coverage threshold). This keeps
v1.2 to "frozen missingness ONLY."

**Exact schema change (`manifest.schema.json`) — the ONLY delta:**

1. New **required** field `design.parameters.missingness_policy ∈ {ineligible, impute_cohort_mean}`.
   Add the property to `design.parameters.properties` and add `"required": ["missingness_policy"]` to
   the `design.parameters` object (base-level required; the switchback `allOf` already adds its own
   required list and composes with this). `ineligible` = a cohort-epoch with a missing outcome or
   covariate is dropped before estimation (`panel.py`); `impute_cohort_mean` = deterministic
   cohort-mean fill. No `evidence_schedule`, no `missingness_action`, no equality constraint, no new

2. **Version bump:** `spec_version "1.0.0" → "1.2.0"` **and** `manifest_version "1.0.0" → "1.2.0"`.

   bump `spec_version` only, leaving `manifest_version "1.0.0"` → golden `b6702e9c…`. Rejected as

## Slot S3 — clarifying items (cheap; they exist because an ambiguity already misfired)

### C1 — state the absolute-allocation property normatively (HASH-NEUTRAL, adoptable alone)

Add to `reward-policy.md` Stage 1 step 6, as a named normative property (text already drafted
non-normatively as "Property P-ABS", Appendix B.1):

> **P-ABS (absolute allocation).** `alloc_c` is a function of cohort `c`'s own `conservative_c_s`
> alone. `overflow_policy` applies the single scalar factor `min(1, B/S)` uniformly to every cohort
> and can only reduce allocations; in the `S ≤ B` branch it is a no-op. Total payout `Σ_c budget_c` is
> **never** normalized up to `B`; the deployment fraction `S/B` is an outcome, not a target. Removing
> a cohort from the paid set can never increase any other cohort's `budget_c` above its own
> `alloc_c`.

**Cost: zero.** This restates existing behavior in existing normative text; it adds no field, changes
no arithmetic, and moves **no** hash. It can be applied independently of the rest of v1.2 the moment
the owner says so. Its whole purpose is that the absence of this sentence is what let a normalized
mental model take hold.

### C2 — rename `overflow_policy` const (HASH-MOVING, cheap)

`proportional_scale_to_budget` → **`scale_down_to_budget_cap`** (or `cap_proportional_scale_down`).
The value is a frozen manifest const, so the rename moves the manifest hash and must ride inside the
package. Recommended because the current name is the proximate cause of the misreading; the schema
`description` is already correct ("scale all allocations down by the single factor min(1, budget/sum)")
but names travel further than descriptions. Cost is computable on request once a name is chosen.

### C3 — curve well-formedness constraint (HASH-NEUTRAL *or* hash-moving depending on form)

Open question **Q-CURVE-1** (`reward-policy.md` Appendix B.4): nothing today ties `reward_curve`
outputs to `budget_base_units` or `estimand.cohort_definition.cohort_count`. Three forms, ordered by
cost:

| Form | Rule | Cost |
| --- | --- | --- |
| **C3-a** | verifier/producer **WARNING** only when `y_last > budget_base_units` | zero — no schema change, no hash move |
| **C3-b** | **hard** schema/producer constraint `y_last ≤ budget_base_units` | zero hash move *by itself*, but it **invalidates the current example manifest** (`y_last = 120e9 > B = 100e9`), forcing an example re-freeze ⇒ new manifest golden |
| **C3-c** | new frozen `reward_policy.expected_paying_cohorts` used to sanity-check `y_last · expected_paying_cohorts` against `B` at freeze | new required field ⇒ hash-moving |

**Recommendation: C3-a for v1.2** (warn, don't forbid). A curve that can pay one cohort more than the
whole budget is *legal and sometimes intended* (winner-take-most designs), and the overflow cap makes
it safe; but it should never be adopted silently. C3-b/C3-c should wait until the C-R study arm shows

## Item B1 — pin the participant Merkle leaf form + sort key (§6.2) — INDEPENDENT of the package

**Currently:** `serialization.md` §6.2 stamps the participant leaf/sort as
`PROVISIONAL-UNPINNED-6.2` ("recommendation of record: participant id ascending"). The
`backend-data-engineer` bundle assembler already implements a concrete form; this item pins THAT form
as normative so the participant root is reproducible.

**Exact spec change (`serialization.md` §6.2, replacing the participant bullet):**

- **participant leaf preimage:** `canonical_leaf_bytes(p) = CJSON({"cohort_id": <string>,
  "participant_id": <string>})` — a §3 CJSON object (two ASCII keys; `cohort_id` sorts before
  `participant_id`). `leaf_hash(p) = SHA-256(0x00 || "CRP:participant:v1" || canonical_leaf_bytes(p))`
  (§6.1, `DOMAIN_TAG = CRP:participant:v1`, already in the domain-tag table).
- **sort key (total order):** `participant_id` ascending by **UTF-16 code-unit of the NFC-normalized
  id** (the same anti-insertion-order rule as assignment §6.2 / `cohort_id`). `participant_id` is a
  unique key within one experiment's participant set, so the order is total with no tie-break; a
  duplicate `participant_id` is a hard error. (If a future variant ever admits the same participant in
  two cohorts as two leaves, the sort key becomes `(participant_id, cohort_id)` — a versioned change,
  not this pin.)

**Why it moves a golden:** it pins the **participant root** and therefore the
`bundle_logical_hash` (`serialization.md` §8.1). It does **NOT** move the manifest golden
`74e0bb82…` or the evidence golden `901b08d5…` — the participant root is a bundle root, not a manifest
field. No participant golden is committed yet, so this is a first pin rather than a change to an
existing committed root; but any bundle that includes `participants.parquet` acquires a fixed
participant root on ratification, and that fixture must then be frozen.

**Computed cost (illustrative fixture, so the user sees concrete bytes):**
- one leaf: `CJSON({"cohort_id":"u4pruydqqvj","participant_id":"sensor-000007"})` →
  `leaf_hash = b559ceec313c46b03d1804e2a4d9f3a916a193dadf9a20fed805d9dec99b1be8`.
- two-leaf tree, participants `sensor-000007` and `sensor-000042` (same cohort), placed in the
  pinned `participant_id`-ascending order (`…007` before `…042`) →
  **participant root `f32410c11cec46460eae4c0a282dd0eecfeed1e81c0216584cec7bb1b844018b`**.
- manifest golden: **UNCHANGED** (`74e0bb82…`).

**Owner:** `verifier-reproducibility-engineer` (commits the first participant golden fixture under
`test-vectors/`), with `backend-data-engineer` confirming the assembler emits the identical leaf form.

**Acceptance check:** the verifier reproduces the participant root from `participants.parquet` alone;
a committed `test-vectors/participant/*` fixture pins it; `serialization.md` §6.2 loses the
`PROVISIONAL-UNPINNED-6.2` stamp.

**Because B1 does not touch the manifest hash, it can ratify on its own schedule** — it is the one
item exempt from the single-package rule.
